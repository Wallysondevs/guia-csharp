C# .NET: SDK, Runtime e CLR

O C# é a linguagem; o .NET é a plataforma que transforma o seu código em programa e o faz rodar. Quem procura "instalar C#" acaba instalando ".NET SDK", e nos tutoriais aparecem siglas como CLR, IL e JIT. Nesta aula você abre o .NET instalado no computador da Ana, vê o que tem dentro do arquivo que o compilador cria e assiste o .NET transformando o seu código em instruções do processador.

Você vai aprender
  • A diferença entre o SDK (para quem programa) e o Runtime (para quem só roda programas).
  • O que fazem o Roslyn (o compilador), a IL (a linguagem intermediária), o CLR (o motor) e o JIT (o tradutor de última hora).
  • O que é a biblioteca de classes e de onde vem o Console.
  • Como ver o que está instalado com dotnet --list-sdks e dotnet --list-runtimes.
  • O que são os arquivos .dll, .pdb e .runtimeconfig.json que o build cria.
  • A diferença entre .NET, .NET Core, .NET Framework e Mono.

Todas as saídas desta aula vêm da máquina da Ana: Ubuntu 26.04 com o pacote dotnet-sdk-10.0 do próprio Ubuntu. Se você ainda não instalou o .NET, pode ler esta aula do mesmo jeito; a instalação vem logo depois, em Instalar no Linux.

A ideia: a receita em língua universal

Imagine uma rede de restaurantes com cozinhas no Brasil, no Japão e na Alemanha. A chef escreve as receitas em português, mas os cozinheiros de cada país falam línguas diferentes. Em vez de escrever três versões, a rede faz assim:

  1. Um tradutor oficial passa a receita do português para uma língua universal da rede, simples e exata, que todo cozinheiro da rede aprendeu.
  2. Em cada país, o cozinheiro lê a receita universal e, na hora de cozinhar, vai traduzindo cada passo para o jeito da cozinha dele, com os fogões e panelas que ele tem.
  3. Os ingredientes básicos (farinha, sal, ovos) já estão na despensa de toda cozinha da rede: a receita só diz "use farinha", sem explicar como fazer farinha.

O .NET funciona exatamente assim:

No restauranteNo .NETNome técnico
A receita em portuguêsO seu código C#código-fonte (ola.cs)
O tradutor oficialO compilador de C#Roslyn
A receita na língua universalO programa traduzido, guardado num arquivo .dllIL (Intermediate Language, linguagem intermediária)
O cozinheiro de cada paísO motor que roda o programa naquele computadorCLR (Common Language Runtime)
Traduzir cada passo na hora de cozinharTransformar a IL em instruções do processador enquanto o programa rodaJIT (just-in-time, "bem na hora")
A despensa com os ingredientes básicosMilhares de classes prontas: Console, Math, List, File…biblioteca de classes (BCL)
Limpar a mesa quando o cliente vai emboraRecolher a memória que o programa não usa maiscoletor de lixo (GC, garbage collector)

A grande vantagem: o mesmo arquivo .dll roda no Linux, no Windows e no macOS, em processadores Intel, AMD ou ARM. Quem se adapta a cada computador é o CLR, não o seu programa.

Do .cs ao programa: o caminho completo

Quando a Ana digita dotnet run ola.cs, acontecem estas etapas, nesta ordem:

  1. O SDK prepara o build. O MSBuild descobre o que precisa ser compilado e com quais bibliotecas.
  2. O Roslyn compila. Ele lê o ola.cs, confere tudo (tipos, nomes, ponto e vírgula) e, se não houver erro, escreve a IL num arquivo ola.dll. Se houver erro, para aqui, e nada roda.
  3. O CLR carrega o programa. Ele abre o ola.dll e as bibliotecas que ele usa (como o System.Console.dll).
  4. O JIT traduz. Na primeira vez que cada método é chamado, o JIT transforma a IL dele em instruções do processador (x64, no computador da Ana) e guarda o resultado na memória.
  5. O processador executa essas instruções, e o texto aparece na tela.

O dotnet run esconde os arquivos que cria. O comando dotnet build faz só as etapas 1 e 2, e diz onde guardou o resultado:

$ dotnet build ola.cs
  Determinando os projetos a serem restaurados...
  Todos os projetos estão atualizados para restauração.

O ola é um programa do Linux (ELF, para processador x86-64). Já o ola.dll o file chama de "executável do Windows", com a etiqueta Mono/.Net assembly: ele usa o mesmo formato de arquivo dos programas do Windows (que começam com as letras MZ, as iniciais de um engenheiro da Microsoft dos anos 1980), mas por dentro não tem instruções de processador nenhum, só IL. Por isso o mesmo ola.dll roda em qualquer sistema. Um arquivo assim, com IL e metadados, se chama assembly no mundo .NET.

Dá para rodar o programa pronto de dois jeitos, sem compilar de novo:

$ ./ola                                         « pelo lançador
Olá, mundo!
$ dotnet ola.dll                                « entregando o .dll direto ao dotnet
Olá, mundo!

Por dentro: a IL e o JIT

Vamos seguir um método pequeno do código-fonte até o processador. Este programa tem um método Somar, que soma dois números (os métodos têm aula própria, Métodos; por enquanto, leia Somar(2, 3) como "some 2 e 3"):

Console.WriteLine(Conta.Somar(2, 3));

static class Conta
{
    public static int Somar(int a, int b) => a + b;
}

$ dotnet run soma.cs
5

1. O que o Roslyn escreveu: a IL

Dentro do soma.dll, o método Somar virou só quatro bytes de IL: 02 03 58 2A (lidos com um programa de reflexão, assunto da aula Reflexão). Cada byte é uma instrução da "língua universal":

ByteInstrução de ILO que faz
02ldarg.0"Pegue o argumento 0" (o a) e ponha numa pilha de trabalho
03ldarg.1"Pegue o argumento 1" (o b) e ponha na pilha
58addTire os dois de cima da pilha, some e ponha o resultado de volta
2AretDevolva o que está na pilha

Repare que a IL não fala de nenhum processador: ela não sabe se vai rodar num Intel, num ARM do celular ou num Mac. É o "passo a passo universal" da receita.

2. O que o JIT fez: código de máquina

O .NET tem uma chave de diagnóstico, a variável DOTNET_JitDisasm, que pede ao JIT para mostrar o que ele gerou para um método. A Ana pediu o Somar (o -c Release pede a versão "de entrega", sem os extras de depuração, para a listagem ficar menor):

$ DOTNET_JitDisasm=Somar dotnet run soma.cs -c Release
; Assembly listing for method Conta:Somar(int,int):int (Tier0)
; Emitting BLENDED_CODE for generic X64 + VEX on Unix
; Tier0 code
; rbp based frame
; partially interruptible
; compiling with minopt

G_M000_IG01:                ;; offset=0x0000
       push     rbp
       sub      rsp, 16
       lea      rbp, [rsp+0x10]
       mov      dword ptr [rbp-0x04], edi       « guarda o a
       mov      dword ptr [rbp-0x08], esi       « guarda o b

G_M000_IG02:                ;; offset=0x0010
       mov      eax, dword ptr [rbp-0x04]       « pega o a
       add      eax, dword ptr [rbp-0x08]       « soma o b: aqui está o a + b

G_M000_IG03:                ;; offset=0x0016
       add      rsp, 16
       pop      rbp
       ret                                      « devolve o resultado

; Total bytes of code 28

5                                               « só agora o Somar roda e o resultado aparece

Isso é código de máquina x64 de verdade, escrito na forma legível (assembly): as instruções que o processador Intel/AMD da Ana executou. Os 4 bytes de IL viraram 28 bytes de instruções do processador. Você não precisa entender cada linha; repare só no add, que é o a + b do seu código, e em três detalhes da primeira parte:

  • Tier0: "nível 0". Na primeira vez, o JIT traduz rápido, sem caprichar, para o programa começar logo. Se o método for chamado muitas vezes, o .NET o traduz de novo, agora caprichando (o "nível 1"). Isso se chama compilação em camadas.
  • X64 e on Unix: o JIT gerou código para o processador e o sistema desta máquina. No Mac com chip M, a mesma IL viraria código ARM64.
  • A listagem aparece antes do 5: o JIT traduz o Somar na primeira vez que ele é chamado, um instante antes de rodar. Só depois a conta é feita e o 5 chega à tela.

E o coletor de lixo?

Enquanto o programa roda, ele cria textos, listas e objetos na memória. O CLR acompanha tudo isso e, de tempos em tempos, o coletor de lixo passa recolhendo o que ninguém usa mais, para a memória não acabar. Você não precisa fazer nada; é por isso que o C# é chamado de linguagem gerenciada. A aula Memória e Coletor de Lixo mostra o coletor trabalhando.

Muitos nomes, um .NET só

O .NET mudou de nome algumas vezes, e a internet está cheia de material de todas as épocas. Este é o mapa:

NomeÉpocaRoda emSituação hoje
.NET Framework (1.0 a 4.8.1)2002 em dianteSó WindowsAinda vem no Windows e roda muito programa antigo, mas não ganha novidades. Fica parado no C# 7.3.

Qual usar? Para programas novos, sempre o .NET atual (hoje, o .NET 10). O .NET Framework só faz sentido para manter um programa antigo do Windows que já usa ele. Quando um tutorial disser "crie um projeto .NET Framework", ou mostrar um caminho como C:\Windows\Microsoft.NET\Framework, ele é dessa época antiga.

Quem faz o seu .NET

O código do .NET é aberto, então outras empresas podem compilá-lo. O .NET da Ana não foi baixado do site da Microsoft: foi a Canonical, a empresa do Ubuntu, que o compilou a partir do código-fonte e o colocou no repositório do Ubuntu. Por isso as versões são um pouco diferentes: no mesmo mês, o site da Microsoft tinha o SDK 10.0.402 com o Runtime 10.0.13, e o Ubuntu, o SDK 10.0.112 com o Runtime 10.0.12. Os dois são o mesmo .NET 10 e o mesmo C# 14; a aula Versões explica os números e a aula Instalar no Linux mostra as duas formas de instalar.

O que significa: esta mensagem sai em inglês, porque vem do "anfitrião" do .NET, a parte mais básica, que não tem tradução. Ela diz: "não consegui carregar o comando, talvez porque você quis rodar um aplicativo chamado run (que não existe) ou um comando do SDK, mas nenhum SDK foi encontrado". O Runtime sabe rodar programas prontos (o ~/rt/dotnet ola.dll funciona), mas o run, o build e o new moram no SDK.

Como consertar: instale o SDK, e não só o Runtime: no Ubuntu, sudo apt install dotnet-sdk-10.0 (aula Instalar no Linux).

Instalou o ".NET Framework" pensando que era o .NET

O que acontece: no Windows, sites antigos e alguns programas pedem o ".NET Framework 4.8". Ele não serve para este guia: não tem o comando dotnet nem o C# 14. No Linux e no macOS, ele nem existe.

Como consertar: instale o .NET SDK 10 (aula Instalar no Windows e macOS). Os dois podem ficar instalados juntos no Windows sem problema.

Resumo

  • O .NET é a plataforma por baixo do C#. O SDK é para quem programa (compilador e comandos); o Runtime é para quem só roda programas. O SDK já traz o Runtime.
  • O caminho: o Roslyn compila o .cs para IL num .dll; o CLR carrega o .dll; o JIT traduz a IL para o processador na hora de rodar.
  • O Console e as outras classes prontas vêm da biblioteca de classes, nos 172 .dll do Runtime. O coletor de lixo cuida da memória.
  • dotnet --list-sdks e dotnet --list-runtimes mostram o que está instalado. No Ubuntu, tudo fica em /usr/lib/dotnet.
  • .NET Framework (só Windows, antigo), Mono, .NET Core e .NET 5 a 10 são a mesma família; o guia usa o .NET 10.

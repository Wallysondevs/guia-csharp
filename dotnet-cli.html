C# O Comando dotnet

Até aqui você usou o dotnet para duas ou três coisas: dotnet run, dotnet new console, dotnet build. Mas ele faz muito mais: cria projetos de vários tipos, baixa pacotes, roda testes, arruma a formatação do código, recompila sozinho quando você salva um arquivo e prepara o programa para entregar. Tudo pelo mesmo comando. Nesta aula você vai conhecer o dotnet por inteiro: como ele é organizado, como pedir ajuda a ele e os comandos que você vai usar todo dia.

Você vai aprender
  • O formato de todo comando: dotnet comando argumentos opções.
  • A descobrir o que está instalado: --version, --list-sdks, --list-runtimes, --info e dotnet sdk check.
  • A pedir ajuda: dotnet --help e dotnet run --help.
  • Os comandos do dia a dia: new, build, run e clean, com as opções mais usadas (-c Release, -v q, --).
  • dotnet watch (recompila sozinho) e dotnet format (arruma o código).
  • Os erros mais comuns: o comando digitado errado, MSB1003 e MSB1011.

Todas as saídas desta aula são reais, feitas na máquina fictícia da Ana, com o .NET 10 SDK do próprio Ubuntu (10.0.112) e o Ubuntu em português: por isso a maior parte das mensagens sai traduzida. Na sua máquina, os números de versão e os tempos podem ser outros. Os comandos rodam no terminal, não no editor do guia (veja Instalar no Linux).

A ideia: um controle remoto universal

Imagine um controle remoto que liga a TV, o som e o ar-condicionado. São aparelhos diferentes, mas você usa sempre o mesmo controle: escolhe o aparelho e aperta o botão. O dotnet é esse controle. Ele não compila nada sozinho: ele é um porteiro (o nome técnico é driver, "condutor") que recebe o seu pedido e chama a ferramenta certa:

Você digitaO dotnet chama
dotnet buildO MSBuild, o "construtor" de projetos, que chama o compilador de C# (o Roslyn).
dotnet newO sistema de modelos, que copia os arquivos de um projeto novo.
dotnet package addO NuGet, que baixa bibliotecas da internet (veja Pacotes NuGet).
dotnet testO executor de testes (veja Testes).
dotnet Programa.dllO runtime, que roda um programa já compilado (veja .NET: SDK, Runtime e CLR).

Por isso o dotnet também é chamado de CLI do .NET (de Command-Line Interface, "interface de linha de comando").

1. O formato de um comando

Todo comando do dotnet tem as mesmas partes, sempre nesta ordem:

$ dotnet build -c Release
«dotnet = o programa · build = o comando · -c Release = uma opção com o seu valor»
dotnet
O programa (o "controle remoto").
comando
O que fazer: new, build, run, test… Alguns têm subcomandos: dotnet new list, dotnet package add, dotnet sdk check.
argumentos
Sobre o que fazer, sem traço na frente: em dotnet new console, o console é o argumento (o modelo).
opções
Como fazer. Começam com traço: um traço e uma letra (-c, -o, -v) ou dois traços e uma palavra (--configuration, --output, --verbosity). São a mesma coisa: -c Release = --configuration Release.

Sem comando, o dotnet só lembra o básico (esta parte não foi traduzida no Ubuntu):

$ dotnet

Usage: dotnet [path-to-application]
Usage: dotnet [commands]

path-to-application:
  The path to an application .dll file to execute.

commands:
  -h|--help                         Display help.
  --info                            Display .NET information.
  --list-runtimes [--arch <arch>]   Display the installed runtimes matching the host or specified architecture. Example architectures: arm64, x64, x86.
  --list-sdks [--arch <arch>]       Display the installed SDKs matching the host or specified architecture. Example architectures: arm64, x64, x86.

2. O que está instalado

Antes de pedir ajuda num fórum, a primeira pergunta é sempre "qual versão você tem?". Quatro comandos respondem:

$ dotnet --list-sdks

$ dotnet --list-runtimes

Microsoft.NETCore.App 10.0.12 [/usr/lib/dotnet/shared/Microsoft.NETCore.App]
dotnet --version
A versão do SDK em uso: o kit para criar programas (compilador, modelos, MSBuild). 10.0.1xx é a primeira "faixa" de SDKs do .NET 10.

dotnet --list-runtimes

4. Os comandos do dia a dia

O dotnet new cria projetos (e arquivos soltos) a partir de modelos (em inglês, templates). Para ver todos, dotnet new list. A lista do SDK da Ana tem 46 modelos; aqui estão os que este guia usa:

A opção -o (output, "saída") escolhe a pasta, e o nome do projeto vem dela (veja Projetos):

$ dotnet new console -o Saudacao

"Restaurar" é baixar (ou conferir) os pacotes de que o projeto precisa. Os comandos build, run e test já restauram sozinhos; o dotnet restore existe para quando você quer só essa etapa.

dotnet run e os argumentos

A Ana trocou o Program.cs do projeto Saudacao para cumprimentar quem for passado na linha de comando (veja Argumentos da Linha de Comando):

Console.WriteLine($"Recebi {args.Length} argumento(s).");
foreach (string a in args)
{
    Console.WriteLine($"Olá, {a}!");
}

$ dotnet run -- Ana Beto
Recebi 2 argumento(s).
Olá, Ana!
Olá, Beto!
$ dotnet run Ana Beto
Recebi 2 argumento(s).
Olá, Ana!
Olá, Beto!
$ dotnet run -- --help
Recebi 1 argumento(s).
Olá, --help!
dotnet run -- Ana Beto
O -- (dois traços sozinhos) é uma divisória: o que vem antes é para o dotnet; o que vem depois vai inteiro para o seu programa, em args.
dotnet run Ana Beto
Sem o -- também funcionou: o dotnet run passa adiante os argumentos que ele não reconhece.
dotnet run -- --help
Aqui o -- faz diferença. Sem ele, dotnet run --help mostraria a ajuda do dotnet run (seção 3). Com ele, o --help chegou ao programa da Ana. Regra simples: use sempre o -- antes dos argumentos do seu programa.

Missão: esta caixa roda o programa como dotnet run -- Ana Beto Carla. Por enquanto ele só conta os argumentos. Acrescente o foreach que mostra Olá, NOME! para cada um, como no Program.cs acima. A saída tem de ter Olá, Carla!.

Console.WriteLine($"Recebi {args.Length} argumento(s).");

Console.WriteLine($"Recebi {args.Length} argumento(s).");
foreach (string a in args)
{
    Console.WriteLine($"Olá, {a}!");
}

O dotnet watch run ("vigie e rode") fica de olho nos arquivos do projeto e roda o programa de novo a cada vez que você salva. 6. dotnet format: arrumar o código

O dotnet format arruma espaços, recuos e chaves de todos os arquivos do projeto, no estilo padrão do C# (veja Sintaxe). A Ana escreveu um arquivo com pressa:

static class Feio {
public static int   Dobro( int x ){return x*2;}
}

Com --verify-no-changes ("confira, sem mudar nada"), ele só aponta o que mudaria:

$ dotnet format --verify-no-changes; echo "código de saída: $?"
/home/ana/projetos/Saudacao/Feio.cs(1,18): error WHITESPACE: Corrigir a formatação de espaço em branco. Substituir 1 caracteres por '\n'. [/home/ana/projetos/Saudacao/Saudacao.csproj]
/home/ana/projetos/Saudacao/Feio.cs(2,1): error WHITESPACE: Corrigir a formatação de espaço em branco. Inserir "\s\s\s\s". [/home/ana/projetos/Saudacao/Saudacao.csproj]
/home/ana/projetos/Saudacao/Feio.cs(2,19): error WHITESPACE: Corrigir a formatação de espaço em branco. Excluir 2 caracteres. [/home/ana/projetos/Saudacao/Saudacao.csproj]
«… mais 7 linhas parecidas …»
código de saída: 2

Cada linha diz o arquivo, a posição (linha, coluna) e o conserto: "substituir por \n" é quebrar a linha; \s\s\s\s são 4 espaços de recuo. O código de saída 2 quer dizer "há o que arrumar". Sem a opção, ele arruma de verdade, em silêncio:

$ dotnet format
$ cat Feio.cs
static class Feio
{
    public static int Dobro(int x) { return x * 2; }
}
$ dotnet format --verify-no-changes; echo "código de saída: $?"
código de saída: 0

Equipes costumam rodar o dotnet format --verify-no-changes automaticamente antes de aceitar uma mudança no código: se ele sair com código diferente de 0, alguém esqueceu de formatar.

Quando dá errado

Comando digitado errado: Não foi possível executar porque o comando ou arquivo especificado não foi encontrado. 
$ dotnet biuld
Não foi possível executar porque o comando ou arquivo especificado não foi encontrado.
Os possíveis motivos para isso incluem:
  * Você digitou incorretamente um comando dotnet interno.
  * Você pretendia executar um programa .NET, mas dotnet-biuld não existe.
  * Você pretendia executar uma ferramenta global, mas não foi possível encontrar um executável com prefixo dotnet com esse nome no PATH.

O que aconteceu: biuld não é um comando. Como o dotnet aceita ferramentas extras (instaladas com dotnet tool), ele também procurou um programa chamado dotnet-biuld, e não achou.

Como resolver: confira a grafia com dotnet --help.

Modelo digitado errado: Nenhum modelo ou subcomando encontrado correspondente 
$ dotnet new consle
Nenhum modelo ou subcomando encontrado correspondente: 'consle'.
Você quis dizer um dos seguintes modelos?
   dotnet new console

Para listar modelos instalados semelhantes a 'consle', execute:
   dotnet new list consle
Para pesquisar os modelos no NuGet.org, execute:
   dotnet new search consle


Para obter detalhes sobre o código de saída, consulte https://aka.ms/templating-exit-codes#103

O que aconteceu e como resolver: aqui o dotnet é mais esperto e já sugere o certo: dotnet new console.

Não foi possível localizar um projeto para executar e error MSB1003 
$ dotnet run
Não foi possível localizar um projeto para executar. Verifique se existe um projeto em /home/ana ou passe o caminho para o projeto usando --project.
$ dotnet build
MSBUILD : error MSB1003: Especifique um arquivo de solução ou de projeto. O diretório de trabalho atual não contém um arquivo de solução ou de projeto.

O que aconteceu: a Ana estava na pasta pessoal (~), que não tem nenhum .csproj. Os comandos run, build, test e clean procuram o projeto na pasta atual.

Como resolver: entre na pasta do projeto (cd ~/projetos/Saudacao) ou diga onde ele está: dotnet run --project ~/projetos/Saudacao. Para um arquivo solto, dê o nome dele: dotnet run ola.cs.

error MSB1011: Especifique o arquivo de solução ou de projeto a usar porque esta pasta contém mais de um arquivo de solução ou de projeto. 
$ cp Saudacao.csproj Outro.csproj
$ dotnet build
MSBUILD : error MSB1011: Especifique o arquivo de solução ou de projeto a usar porque esta pasta contém mais de um arquivo de solução ou de projeto.

O que aconteceu: a pasta tem dois .csproj (ou um .csproj e uma solução .slnx), e o dotnet não sabe qual usar.

Como resolver: diga o nome: dotnet build Saudacao.csproj. Melhor ainda: cada projeto na sua própria pasta (veja Soluções e Vários Projetos).

Resumo

  • O dotnet é um porteiro: recebe o pedido e chama a ferramenta certa (MSBuild, modelos, NuGet, testes, runtime).
  • Formato: dotnet comando argumentos opções. Opções curtas (-c) e longas (--configuration) são a mesma coisa.
  • --version, --list-sdks, --list-runtimes, --info e sdk check dizem o que está instalado.
  • Na dúvida, dotnet --help e dotnet COMANDO --help.
  • build -c Release compila a versão final; run -- argumentos passa argumentos ao programa; clean apaga o que foi compilado.
  • watch run roda de novo a cada arquivo salvo; format arruma o código.
  • run, build e test procuram o projeto na pasta atual: entre nela ou use --project.

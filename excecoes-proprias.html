C# Exceções Próprias

O .NET tem exceções para os problemas de qualquer programa: argumento inválido, arquivo que não existe, divisão por zero. Mas a lojinha da Ana tem problemas que só ela tem: "o estoque não dá para este pedido", "este produto não está cadastrado". Nesta aula você vai criar as suas próprias classes de exceção, com nome, mensagem e dados que fazem sentido no seu programa, e organizar várias delas numa família.

Você vai aprender
  • Criar uma exceção: uma classe que herda de Exception e passa a mensagem para base.
  • As regras de nome e de herança que todo programador C# segue.
  • Guardar dados extras (o produto, a quantidade) em propriedades da exceção.
  • Os três construtores de costume, inclusive o que recebe a InnerException.
  • Montar uma família: uma exceção mãe do programa e as filhas, capturadas juntas.
  • Quando vale a pena criar uma exceção, e quando uma do .NET basta.
  • Os erros CS0029, CS0155, CS1729 e CS8864.

Esta aula usa herança (: Exception), construtores e base. Todos os programas rodaram na máquina da Ana, com o .NET 10 (C# 14), usando dotnet run arquivo.cs na pasta ~/cs.

A ideia antes do código

Num hospital, "deu um problema" não ajuda ninguém. Os avisos têm nome: "código azul", "código vermelho". Cada nome diz o que aconteceu e chama a equipe certa. Quem é da cardiologia corre para o código azul e ignora os outros.

Uma exceção própria é um aviso com nome. Em vez de lançar uma InvalidOperationException genérica para "estoque insuficiente", a lojinha lança uma EstoqueInsuficienteException. Quem chama pode capturar exatamente esse problema com catch (EstoqueInsuficienteException), sem pegar sem querer os outros.

1. A menor exceção possível

Uma exceção é uma classe como outra qualquer, com uma exigência: ela tem de ser da família Exception.

Vender("caderno", 5, 2);

void Vender(string produto, int pedido, int emEstoque)
{
    if (pedido > emEstoque)
    {
        throw new EstoqueInsuficienteException($"Pedido de {pedido} {produto}(s), mas só há {emEstoque}.");
    }
    Console.WriteLine("Vendido!");
}

class EstoqueInsuficienteException : Exception
{
    public EstoqueInsuficienteException(string mensagem) : base(mensagem)
    {
    }
}

2. Dados extras: o que o catch precisa saber

A grande vantagem de ter a sua classe é poder guardar dados nela. Quem captura a exceção não precisa "ler" a mensagem para descobrir quantas unidades havia: a informação está numa propriedade.

try
{
    Loja.Vender("caderno", 5);
}
catch (EstoqueInsuficienteException e)
{
    Console.WriteLine(e.Message);
    Console.WriteLine($"Que tal levar só {e.Disponivel}?");
}

static class Loja
{
    static readonly Dictionary<string, int> estoque = new() { ["caderno"] = 2, ["caneta"] = 40 };

    public static void Vender(string produto, int pedido)
    {
        int disponivel = estoque[produto];
        if (pedido > disponivel)
        {
            throw new EstoqueInsuficienteException(produto, pedido, disponivel);
        }
        estoque[produto] = disponivel - pedido;
        Console.WriteLine($"Vendido: {pedido} {produto}(s)");
    }
}

class EstoqueInsuficienteException : Exception
{
    public string Produto { get; }
    public int Pedido { get; }
    public int Disponivel { get; }

    public EstoqueInsuficienteException(string produto, int pedido, int disponivel)
        : base($"Pedido de {pedido} {produto}(s), mas só há {disponivel}.")
    {
        Produto = produto;
        Pedido = pedido;
        Disponivel = disponivel;
    }
}

$ dotnet run dados.cs
Pedido de 5 caderno(s), mas só há 2.
Que tal levar só 2?
public int Disponivel { get; }
Uma propriedade só de leitura (aula readonly e init): quem captura lê, mas não muda. Exceções carregam fatos sobre o que aconteceu; não faz sentido alterá-los depois.
EstoqueInsuficienteException(string produto, int pedido, int disponivel)
Agora o construtor recebe os dados, não a mensagem pronta. Quem lança só diz o que aconteceu: new EstoqueInsuficienteException(produto, pedido, disponivel).
: base($"Pedido de {pedido} …")
A exceção monta a própria mensagem a partir dos dados. Assim, todas as mensagens desse problema saem no mesmo formato, em qualquer lugar do programa.
e.Disponivel
No catch, a informação vem pronta, como número. Dá para oferecer uma alternativa ao cliente, sem precisar "garimpar" o 2 de dentro do texto.

Não dá para fazer com record

Uma exceção parece um bom caso para record (só dados, só leitura), mas records só herdam de outros records, e Exception é uma classe. record ProdutoEsgotadoException(string Mensagem) : Exception(Mensagem); dá o erro CS8864 (veja Quando dá errado). Use class.

3. Os três construtores de costume

As exceções do .NET têm, quase todas, três construtores: sem nada, com a mensagem, e com a mensagem e a exceção interna (a InnerException, da aula throw). Numa biblioteca que outras pessoas vão usar, é costume oferecer os mesmos três:

public class LojinhaException : Exception
{
    public LojinhaException() { }
    public LojinhaException(string mensagem) : base(mensagem) { }
    public LojinhaException(string mensagem, Exception interna) : base(mensagem, interna) { }
}
LojinhaException() { }
Sem argumentos. A mensagem fica a padrão do .NET (veja abaixo).
LojinhaException(string mensagem) : base(mensagem)
O mais usado: só a mensagem.
LojinhaException(string mensagem, Exception interna) : base(mensagem, interna)
Para embrulhar uma exceção de baixo nível (um FormatException, um IOException) numa da lojinha, sem perder a original.

Se você não escrever construtor nenhum, a classe ganha só o construtor vazio, e a mensagem fica a genérica do .NET:

try
{
    throw new ProdutoEsgotadoException();
}
catch (ProdutoEsgotadoException e)
{
    Console.WriteLine(e.Message);
}

class ProdutoEsgotadoException : Exception
{
}

$ dotnet run semnome.cs
Exception of type 'ProdutoEsgotadoException' was thrown.

"Uma exceção do tipo ProdutoEsgotadoException foi lançada." Funciona, mas não diz qual produto. E, nessa classe sem construtores, new ProdutoEsgotadoException("…") nem compila (CS1729): construtores não são herdados em C#; cada classe declara os seus.

4. Uma família de exceções

Um programa maior tem vários problemas próprios. O costume é criar uma exceção mãe do programa, e as outras como filhas dela. Assim, quem chama escolhe: capturar um problema específico, ou capturar "qualquer problema da lojinha" de uma vez. E, num projeto, elas moram no namespace do programa:

using Lojinha;

string[] pedidos = ["caneta:3", "caderno:5", "borracha:1"];
foreach (string p in pedidos)
{
    string[] partes = p.Split(':');
    try
    {
        Loja.Vender(partes[0], int.Parse(partes[1]));
    }
    catch (LojinhaException e)
    {
        Console.WriteLine($"Não deu: {e.Message} ({e.GetType().Name})");
    }
}
Loja.Vender("lápis", 1);

namespace Lojinha
{
    class LojinhaException : Exception
    {
        public LojinhaException() { }
        public LojinhaException(string mensagem) : base(mensagem) { }
        public LojinhaException(string mensagem, Exception interna) : base(mensagem, interna) { }
    }

    class EstoqueInsuficienteException : LojinhaException
    {
        public EstoqueInsuficienteException(string produto, int disponivel)
            : base($"só há {disponivel} {produto}(s)") { }
    }

    class ProdutoNaoEncontradoException : LojinhaException
    {
        public ProdutoNaoEncontradoException(string produto)
            : base($"\"{produto}\" não está cadastrado") { }
    }

    static class Loja
    {
        static readonly Dictionary<string, int> estoque = new() { ["caderno"] = 2, ["caneta"] = 40 };

        public static void Vender(string produto, int pedido)
        {
            if (!estoque.TryGetValue(produto, out int disponivel))
            {
                throw new ProdutoNaoEncontradoException(produto);
            }
            if (pedido > disponivel)
            {
                throw new EstoqueInsuficienteException(produto, disponivel);
            }
            estoque[produto] = disponivel - pedido;
            Console.WriteLine($"Vendido: {pedido} {produto}(s)");
        }
    }
}

Repare que um FormatException do int.Parse não seria pego pelo catch (LojinhaException e): ele não é da família. É justamente essa a vantagem: o catch pega os problemas da lojinha, que ele sabe tratar, e deixa os defeitos de programação aparecerem.

Criar a sua ou usar uma do .NET?

SituaçãoUse
Um parâmetro null, fora do intervalo, inválidoAs do .NET: ArgumentNullException, ArgumentOutOfRangeException, ArgumentException
O objeto não está pronto para a operaçãoInvalidOperationException

Uma regra prática: crie uma exceção quando você consegue imaginar alguém escrevendo um catch só para ela. Se ninguém nunca vai capturá-la separada, uma do .NET basta.

Quando dá errado

CS0029: a classe esqueceu o : Exception 
throw new ProdutoEsgotado("caderno");

class ProdutoEsgotado
{
    public ProdutoEsgotado(string nome) { }
}

$ dotnet run naoexc.cs
/home/ana/cs/naoexc.cs(1,7): error CS0029: Não é possível converter implicitamente tipo "ProdutoEsgotado" em "System.Exception"

Ocorreu uma falha no build. Corrija os erros de build e execute novamente.

O que significa: o throw só aceita objetos da família Exception, e ProdutoEsgotado não é.

Como consertar: faça a classe herdar de Exception, passe a mensagem para base e, de quebra, ponha o Exception no fim do nome: class ProdutoEsgotadoException : Exception.

CS0155: catch de algo que não é exceção 
try { Console.WriteLine("oi"); }
catch (string e) { }

$ dotnet run catchnao.cs
/home/ana/cs/catchnao.cs(2,8): error CS0155: O tipo caught ou thrown deve ser derivado de System.Exception
/home/ana/cs/catchnao.cs(2,15): warning CS0168: A variável "e" está declarada, mas nunca é usada

Ocorreu uma falha no build. Corrija os erros de build e execute novamente.

O que significa: "o tipo capturado (caught) ou lançado (thrown) deve ser derivado de System.Exception". A tradução deixou duas palavras em inglês, mas a ideia é a mesma do erro anterior, do lado do catch.

Como consertar: no catch, só tipos da família Exception.

CS1729: "não contém um construtor que aceita 1 argumentos" 
throw new ProdutoEsgotadoException("O caderno esgotou.");

class ProdutoEsgotadoException : Exception
{
}

$ dotnet run semctor.cs
/home/ana/cs/semctor.cs(1,11): error CS1729: "ProdutoEsgotadoException" não contém um construtor que aceita 1 argumentos

Ocorreu uma falha no build. Corrija os erros de build e execute novamente.

O que significa: Exception tem um construtor com mensagem, mas a sua classe não herda construtores. Sem nenhum escrito, ela só tem o vazio.

Como consertar: escreva o construtor: public ProdutoEsgotadoException(string mensagem) : base(mensagem) { }.

CS8864: exceção como record 
throw new ProdutoEsgotadoException("O caderno esgotou.");

record ProdutoEsgotadoException(string Mensagem) : Exception(Mensagem);

$ dotnet run rec.cs
/home/ana/cs/rec.cs(3,52): error CS8864: Os registros só podem ser herdados de um objeto ou de outro registro
/home/ana/cs/rec.cs(3,8): error CS0115: "ProdutoEsgotadoException.EqualityContract": não encontrado nenhum método adequado para substituição
/home/ana/cs/rec.cs(3,8): error CS0115: "ProdutoEsgotadoException.Equals(Exception?)": não encontrado nenhum método adequado para substituição
/home/ana/cs/rec.cs(3,8): error CS0115: "ProdutoEsgotadoException.PrintMembers(StringBuilder)": não encontrado nenhum método adequado para substituição

Ocorreu uma falha no build. Corrija os erros de build e execute novamente.

O que significa: o primeiro erro é o que importa: "registros (records) só podem herdar de object ou de outro record". Os três CS0115 são consequência: o compilador tentou gerar os métodos de um record em cima de uma classe que não é record.

Como consertar: use class, com construtor normal ou primário (a forma curta da seção 2).

A mensagem é "Exception of type '…' was thrown."

O que significa: o construtor da sua exceção não repassou a mensagem para base, ou a exceção foi criada com new …() sem argumentos.

Como consertar: confira se o construtor tem : base(mensagem) (e não só guarda a mensagem numa propriedade sua).

Resumo

  • Uma exceção própria é uma classe que herda de Exception e tem o nome terminado em Exception.
  • O construtor repassa a mensagem com : base(mensagem); sem isso, a mensagem é "Exception of type '…' was thrown.". Construtores não são herdados (CS1729).
  • Dados extras vão em propriedades só de leitura; a exceção pode montar a própria mensagem a partir deles.
  • Os três construtores de costume: vazio, com mensagem e com mensagem + InnerException.
  • Uma família (LojinhaException e filhas) deixa quem chama escolher entre um problema específico e todos os do programa.
  • Crie uma exceção quando alguém vai querer um catch só para ela; para parâmetros inválidos, use as do .NET. Exceção é class, nunca record (CS8864).

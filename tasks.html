C# Task

Na aula async e await, cada método assíncrono devolvia uma Task ("tarefa"), e o await esperava por ela. Nesta aula, a tarefa vira a protagonista. Você vai ver o que existe dentro de uma Task, mandar uma conta pesada para outra thread com Task.Run, baixar três arquivos ao mesmo tempo com Task.WhenAll, pegar a loja que responde primeiro com Task.WhenAny e desistir de quem demora demais.

Você vai aprender
  • O que é uma Task, os seus estados (Status) e o Task<T>, que carrega um resultado.
  • Rodar uma conta demorada com Task.Run, sem travar o programa principal.
  • Esperar várias tarefas com Task.WhenAll e receber os resultados em ordem.
  • Criar uma tarefa por item com LINQ (Select) e esperar todas.
  • Pegar a primeira que terminar com Task.WhenAny, e usar isso para desistir depois de um tempo.
  • O que acontece com as exceções de várias tarefas (AggregateException).

Os programas rodam com dotnet run na pasta ~/cs da Ana, num notebook com 8 núcleos. Os tempos medidos variam um pouco de uma execução para outra; quando várias tarefas rodam juntas, a ordem de algumas linhas também pode mudar.

A ideia: a senha da lanchonete

Na lanchonete, você faz o pedido e recebe uma senha. A senha não é o lanche: é a promessa de um lanche. Com ela na mão, você pode sentar, conversar, olhar o celular. Pela senha, dá para saber se o pedido ainda está na fila, se já está pronto ou se deu problema ("acabou o pão"). Quando chamam o seu número, você troca a senha pelo lanche.

Uma Task é essa senha. Um Task<string> é a senha de um string, que você recebe com await. E nada impede você de fazer vários pedidos e ficar com várias senhas ao mesmo tempo: é o que o Task.WhenAll organiza.

TipoSenha de…O await devolve
Taskum trabalho sem resultado (gravar, enviar)nada
Task<int>um int (contar, somar)um int
Task<string>um string (ler, baixar)um string

As classes ficam em System.Threading.Tasks, que já vem incluído.

1. Os estados de uma tarefa

Task espera = Task.Delay(1000);
Console.WriteLine(espera.Status);
Console.WriteLine(espera.IsCompleted);
await espera;
Console.WriteLine(espera.Status);
Console.WriteLine(espera.IsCompleted);

Task<int> pronta = Task.FromResult(42);
Console.WriteLine($"{pronta.Status} {await pronta}");

$ dotnet run status.cs
WaitingForActivation
False
RanToCompletion
True
RanToCompletion 42
Task.Delay(1000)
Uma tarefa que termina daqui a 1 segundo. Sem await na frente, você fica com a tarefa (a senha) na variável.
espera.Status
O estado, um enum TaskStatus. WaitingForActivation ("esperando ser ativada") quer dizer "ainda não terminou". Os principais estados finais são RanToCompletion ("rodou até o fim", deu certo), Faulted ("com defeito", lançou uma exceção) e Canceled (cancelada, aula Cancelamento).
espera.IsCompleted
true quando a tarefa terminou, de qualquer jeito. Também existem IsCompletedSuccessfully (terminou bem) e IsFaulted (deu erro).
Task.FromResult(42)
Uma tarefa que já nasce pronta, com o resultado dentro. Útil quando um método precisa devolver Task<int> mas, às vezes, já tem a resposta (por exemplo, guardada de uma consulta anterior). Para uma Task sem resultado, Task.CompletedTask.

Na prática, você quase nunca olha o Status: o await espera, entrega o resultado e lança a exceção, se houver. Mas ele ajuda a entender o que é uma tarefa: um objeto que diz em que pé está um trabalho.

2. Uma conta pesada: Task.Run

O Task.Delay e os métodos …Async de arquivos e da internet esperam por um "aparelho" (o relógio, o disco, a rede). Mas e se o trabalho demorado é uma conta, o próprio processador trabalhando? Aí o await sozinho não ajuda: alguém tem de fazer a conta. O Task.Run ("rodar tarefa") entrega a conta para uma thread do pool de threads do .NET, um grupo de "ajudantes" que ficam esperando trabalho (aula Threads). Num computador com vários núcleos, várias contas andam ao mesmo tempo:

using System.Diagnostics;

Console.WriteLine($"Programa principal: thread {Environment.CurrentManagedThreadId}");
Stopwatch relogio = Stopwatch.StartNew();
long a = Calcular("A");
long b = Calcular("B");
long c = Calcular("C");
long d = Calcular("D");
Console.WriteLine($"Um depois do outro: {a + b + c + d} em {relogio.Elapsed.TotalSeconds:F1} s");

relogio.Restart();
Task<long>[] tarefas =
[
    Task.Run(() => Calcular("A")),
    Task.Run(() => Calcular("B")),
    Task.Run(() => Calcular("C")),
    Task.Run(() => Calcular("D")),
];
long[] partes = await Task.WhenAll(tarefas);
Console.WriteLine($"Com Task.Run: {partes.Sum()} em {relogio.Elapsed.TotalSeconds:F1} s");

long Calcular(string nome)
{
    Console.WriteLine($"  {nome} na thread {Environment.CurrentManagedThreadId}");
    long soma = 0;
    for (int i = 0; i < 300_000_000; i++)
    {
        soma += i % 7;
    }
    return soma;
}

Recebe uma lambda com o trabalho e o coloca na fila do pool de threads. Devolve na hora um Task<long>, porque a lambda devolve long. Repare: o Calcular é um método comum, sem async.

Cada conta rodou numa thread diferente do pool, ao mesmo tempo que as outras. A ordem das mensagens depende de qual começou primeiro, e muda de uma execução para outra.

Espera as quatro (seção 3) e devolve os quatro resultados num long[].

As contas são as mesmas, e o resultado também (3599999988). Mas, divididas entre núcleos, terminaram em metade do tempo. Não foi 4 vezes mais rápido porque os núcleos dividem outras coisas (a memória, o calor, os outros programas abertos).
No editor do guia, uma thread só

O .NET do editor roda em WebAssembly, dentro do navegador, com uma thread só. Nele, o Task.Run funciona e dá o mesmo resultado, mas todas as contas rodam na thread 1, uma depois da outra, e o tempo não cai. Para ver a diferença de velocidade, rode no seu computador. As missões desta aula usam Task.Delay, que funciona igual nos dois.

3. Várias tarefas: Task.WhenAll

A Ana vai baixar três arquivos. Cada download é uma espera (a rede), simulada aqui com Task.Delay. Em vez de baixar um depois do outro, ela começa os três e espera todos:

using System.Diagnostics;

(string Nome, int Segundos)[] arquivos = [("fotos.zip", 3), ("musica.mp3", 1), ("manual.pdf", 2)];
Stopwatch relogio = Stopwatch.StartNew();

List<Task<int>> tarefas = [];
foreach (var arquivo in arquivos)
{
    tarefas.Add(BaixarAsync(arquivo.Nome, arquivo.Segundos));
}
int[] tamanhos = await Task.WhenAll(tarefas);

for (int i = 0; i < arquivos.Length; i++)
{
    Console.WriteLine($"{arquivos[i].Nome}: {tamanhos[i]} MB");
}
Console.WriteLine($"Total: {tamanhos.Sum()} MB em {relogio.Elapsed.TotalSeconds:F1} s");

async Task<int> BaixarAsync(string nome, int segundos)
{
    Console.WriteLine($"Baixando {nome}...");
    await Task.Delay(segundos * 1000);
    Console.WriteLine($"Pronto: {nome}");
    return segundos * 25;
}

Chamar o método começa o download e devolve a tarefa, que vai para a lista. Ao fim do foreach, os três downloads já estão andando.

Missão: este programa baixa um arquivo de cada vez: o await dentro do foreach espera cada download antes de começar o próximo. Mude-o para começar os três e esperar todos de uma vez: no laço, guarde cada tarefa na lista tarefas (sem await), e depois do laço faça int[] tamanhos = await Task.WhenAll(tarefas);. As três linhas Baixando… devem aparecer seguidas, e o total continua 150 MB.

Uma tarefa por item, com LINQ

"Uma tarefa para cada item da lista" é tão comum que costuma ser escrito numa linha, com o Select da aula Filtrar e Projetar:

(string Nome, int Segundos)[] arquivos = [("fotos.zip", 3), ("musica.mp3", 1), ("manual.pdf", 2)];
int[] tamanhos = await Task.WhenAll(arquivos.Select(a => BaixarAsync(a.Nome, a.Segundos)));
Console.WriteLine(string.Join(" + ", tamanhos) + $" = {tamanhos.Sum()} MB");

async Task<int> BaixarAsync(string nome, int segundos)
{
    await Task.Delay(segundos * 1000);
    return segundos * 25;
}

$ dotnet run linq.cs

O Select transforma cada arquivo numa tarefa (começando o download), e o WhenAll recebe a sequência de tarefas.

4. A primeira que terminar: Task.WhenAny

A Ana quer saber o preço de um produto e pergunta para três lojas. Basta a primeira resposta. E se uma loja demorar demais, ela desiste:

Task<string> lojaA = ConsultarAsync("Loja A", 3000);
Task<string> lojaB = ConsultarAsync("Loja B", 1000);
Task<string> lojaC = ConsultarAsync("Loja C", 2000);

Task<string> primeira = await Task.WhenAny(lojaA, lojaB, lojaC);
Console.WriteLine($"Mais rápida: {await primeira}");

Task<string> lenta = ConsultarAsync("Loja D", 5000);
Task limite = Task.Delay(1500);
if (await Task.WhenAny(lenta, limite) == limite)
{
    Console.WriteLine("Loja D: demorou demais, desisti");
}

async Task<string> ConsultarAsync(string loja, int ms)
{
    await Task.Delay(ms);
    return loja;
}

$ dotnet run lojas.cs
Mais rápida: Loja B
Loja D: demorou demais, desisti
await Task.WhenAny(lojaA, lojaB, lojaC)
"Quando qualquer uma": termina assim que a primeira das tarefas terminar. O resultado do await não é o texto: é a própria tarefa que venceu (um Task<string>).
await primeira
Um segundo await, agora na tarefa vencedora, para pegar o texto. Ela já terminou, então não há espera.
Task limite = Task.Delay(1500);
Um "despertador" de 1,5 segundo.
await Task.WhenAny(lenta, limite) == limite
Uma corrida entre a loja e o despertador. Se o despertador venceu, a loja passou do tempo. É o jeito clássico de pôr um tempo limite (timeout) em qualquer tarefa.

As tarefas que perdem a corrida não param sozinhas: a Loja A e a Loja D continuam "consultando" até o programa terminar. Para parar uma tarefa de verdade, ela precisa aceitar um pedido de cancelamento (aula Cancelamento).

5. Quando uma tarefa falha

Se a tarefa lança uma exceção, ela fica guardada dentro dela (Status = Faulted) e é lançada de novo no await. Com várias tarefas no WhenAll, mais de uma pode falhar:

Task todas = Task.WhenAll(
    EnviarAsync("Ana", 300, true),
    EnviarAsync("Bruno", 100, false),
    EnviarAsync("Carla", 200, true));
try
{
    await todas;
}
catch (Exception e)
{
    Console.WriteLine($"O await lançou: {e.Message}");
}
Console.WriteLine($"Erros guardados na tarefa: {todas.Exception!.InnerExceptions.Count}");
foreach (Exception e in todas.Exception.InnerExceptions)
{
    Console.WriteLine($" - {e.Message}");
}

async Task EnviarAsync(string nome, int ms, bool falha)
{
    await Task.Delay(ms);
    if (falha)
    {
        throw new InvalidOperationException($"E-mail de {nome} não foi enviado");
    }
    Console.WriteLine($"E-mail de {nome} enviado");
}

$ dotnet run excecoes.cs
E-mail de Bruno enviado
O await lançou: E-mail de Carla não foi enviado
Erros guardados na tarefa: 2
 - E-mail de Carla não foi enviado
 - E-mail de Ana não foi enviado
o WhenAll espera todas
Mesmo com erros, ele só termina quando as três terminaram. O e-mail do Bruno foi enviado normalmente.
catch (Exception e)
O await lança uma das exceções (aqui, a da Carla, a primeira a falhar).
todas.Exception
A tarefa guarda todas as exceções numa AggregateException ("exceção agregada", que junta várias). A lista está em InnerExceptions ("exceções internas"). O ! diz ao compilador que ela não é null aqui (sabemos que houve erro).

Quando dá errado

Todas as tarefas mostraram o mesmo número 
List<Task> tarefas = [];
for (int i = 0; i < 3; i++)
{
    tarefas.Add(Task.Run(() => Console.WriteLine($"Tarefa {i}")));
}
await Task.WhenAll(tarefas);

$ dotnet run laco.cs
Tarefa 0
Tarefa 3
Tarefa 3
$ dotnet run laco.cs
Tarefa 3
Tarefa 3
Tarefa 3

O que aconteceu: a lambda não guarda o valor de i no momento em que foi criada: ela guarda a variável i, que é uma só para o for inteiro. As tarefas só rodam um pouquinho depois, quando o laço já terminou e i vale 3. Às vezes uma tarefa é rápida o bastante para pegar o 0. O resultado muda a cada execução, o que torna esse erro difícil de encontrar.

Como resolver: copie o valor para uma variável dentro do laço, que é nova a cada volta: int numero = i; e use numero na lambda. (Com foreach, a variável já é nova a cada volta, desde o C# 5.) A ordem das linhas continua podendo variar, mas cada número aparece uma vez:

$ dotnet run laco2.cs
Tarefa 0
Tarefa 2
Tarefa 1
CS0029: Task<int> não é int 
int n = ContarAsync();
Console.WriteLine(n);

async Task<int> ContarAsync()
{
    await Task.Delay(100);
    return 3;
}

$ dotnet run semawait.cs
/home/ana/cs/semawait.cs(1,9): error CS0029: Não é possível converter implicitamente tipo "System.Threading.Tasks.Task<int>" em "int"

Ocorreu uma falha no build. Corrija os erros de build e execute novamente.

O que aconteceu: o método devolve a senha (Task<int>), e a variável espera o lanche (int).

Como resolver: int n = await ContarAsync();.

.Wait() e .Result: a exceção embrulhada 
Falhar().Wait();

async Task Falhar()
{
    await Task.Delay(100);
    throw new InvalidOperationException("O servidor não respondeu");
}

$ dotnet run wait.cs; echo "código: $?"
Unhandled exception. System.AggregateException: One or more errors occurred. (O servidor não respondeu)
 ---> System.InvalidOperationException: O servidor não respondeu
   at Program.<<Main>$>g__Falhar|0_0() in /home/ana/cs/wait.cs:line 6
   --- End of inner exception stack trace ---
   at System.Threading.Tasks.Task.Wait(Int32 millisecondsTimeout, CancellationToken cancellationToken)
   at System.Threading.Tasks.Task.Wait()

O que aconteceu: o .Wait() ("esperar") e o .Result ("resultado") esperam a tarefa travando a thread, como um Thread.Sleep. E, ao contrário do await, eles embrulham a exceção numa AggregateException ("ocorreram um ou mais erros"), o que complica o catch. Em aplicativos com janelas, travar a thread principal esperando uma tarefa que precisa dela pode congelar o programa para sempre. No editor do guia, que tem uma thread só, esperar assim nem é permitido: o programa para com PlatformNotSupportedException.

Como resolver: use await, e o método que o contém vira async. O .Result só é seguro numa tarefa que você sabe que já terminou (por exemplo, depois de um await Task.WhenAll).

Resumo

  • Uma Task é a "senha" de um trabalho em andamento; o Task<T> carrega um resultado, que o await entrega. O Status diz em que pé ela está.
  • Task.Run manda uma conta pesada para uma thread do pool; várias contas assim usam vários núcleos (no editor do guia, que tem uma thread só, o tempo não cai).
  • Task.WhenAll espera todas e devolve os resultados na ordem das tarefas; o tempo é o da mais longa. Com LINQ: Task.WhenAll(lista.Select(…)).
  • Task.WhenAny devolve a primeira tarefa que terminou; com um Task.Delay na corrida, vira um tempo limite.
  • Exceções ficam guardadas na tarefa e voltam no await; o WhenAll guarda todas em Exception.InnerExceptions.
  • Cuidado com a variável do for dentro da lambda, e prefira await a .Wait() e .Result.

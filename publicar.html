C# Publicar o Programa

O relatório da turma está pronto, testado e funcionando no computador da Ana. Agora a coordenadora da escola quer usá-lo no computador dela, que não tem o SDK do .NET, não tem o código e não sabe o que é dotnet run. Publicar é preparar o programa para isso: compilar a versão final e juntar numa pasta tudo o que ele precisa para rodar em outra máquina. Nesta aula você vai publicar o mesmo programa de cinco jeitos e comparar os tamanhos reais, de 136 KB a 80 MB.

Você vai aprender
  • A usar dotnet publish e a ler o que vai na pasta publish.
  • A diferença entre um programa dependente do .NET e um autocontido (--self-contained), e o que é o -r linux-x64.
  • Um executável só (PublishSingleFile), menor (PublishTrimmed) ou em código nativo (PublishAot).
  • A publicar para o Windows (-r win-x64) a partir do Linux.
  • A publicar um arquivo solto (dotnet publish arquivo.cs) .NET 10.
  • Os erros NETSDK1083 e "You must install or update .NET".

Todas as saídas e todos os tamanhos desta aula são reais, feitos com o .NET 10 SDK (10.0.112) na máquina fictícia da Ana, no programa Escola.Relatorio da aula Bibliotecas de Classes (ele usa a biblioteca Escola.Notas). Os tamanhos mudam um pouco de versão para versão do .NET. Algumas formas baixam pacotes do NuGet na primeira vez e precisam de internet.

A ideia: a marmita e o restaurante

A Ana quer levar o almoço para a coordenadora. Ela tem duas opções:

  • Só a comida, numa marmita pequena. Leve e prática, mas a coordenadora precisa ter prato, talheres e micro-ondas em casa.
  • A comida com prato, talheres e um micro-ondas portátil. Funciona em qualquer lugar, mas a sacola fica enorme.

Publicar um programa é escolher entre essas duas sacolas. A "comida" é o seu código compilado (alguns KB). O "micro-ondas" é o runtime do .NET, o motor que roda programas .NET (dezenas de MB, veja .NET: SDK, Runtime e CLR).

3. Menos arquivos e menos megabytes

Um arquivo só: PublishSingleFile

195 arquivos são incômodos de copiar. A propriedade PublishSingleFile junta tudo num executável. As propriedades do .csproj podem ir na linha de comando com -p:Nome=valor (veja O Arquivo .csproj), e o -o escolhe a pasta de saída:

$ dotnet publish -r linux-x64 --self-contained -p:PublishSingleFile=true -o saida/arquivo-unico

Tirar o que não é usado: PublishTrimmed

O programa da Ana usa uma fração minúscula das 164 bibliotecas System.*. O PublishTrimmed ("publicar aparado") analisa o programa e corta o que ele nunca chama:

"Otimizando montagens (assemblies) para tamanho": de 70 MB para 14 MB, ainda autocontido. O cuidado: o corte é feito por análise do código, e um programa que usa Reflexão (procurar classes e métodos pelo nome, em tempo de execução) pode precisar de algo que foi cortado. O compilador avisa nesses casos com avisos IL2026 e parecidos. Programas pequenos como o da Ana não têm esse problema; sempre teste o executável aparado antes de entregar.

Código nativo: PublishAot

Nas formas anteriores, o executável ainda leva o runtime, que traduz o código do .NET para a linguagem do processador enquanto o programa roda (é o "JIT", veja .NET). Com PublishAot (de Ahead-Of-Time, "antes da hora"), essa tradução é feita na publicação, e o resultado é um executável nativo do Linux, como um programa em C:

$ dotnet publish -r linux-x64 -p:PublishAot=true -o saida/nativo

"Gerando código nativo": o compilador AOT (o ILCompiler, baixado do NuGet na primeira vez) traduziu tudo para instruções do processador. No Linux, ele usa o clang para montar o executável: instale com sudo apt install clang se não tiver.
Escola.Relatorio (1,3 MB)
Um executável nativo, autocontido, sem nenhum .dll ao lado. O --self-contained nem precisou ser escrito: com AOT, é sempre assim.
Escola.Relatorio.dbg
As informações de depuração do código nativo, num arquivo separado. Não vai para a outra máquina.

Além de pequeno, o executável nativo começa a rodar muito mais rápido, porque não tem runtime para iniciar nem código para traduzir:

$ time ./bin/Release/net10.0/publish/Escola.Relatorio > /dev/null

real	0m0,052s
user	0m0,040s
sys	0m0,012s
$ time ./saida/nativo/Escola.Relatorio > /dev/null

real	0m0,005s
user	0m0,000s
sys	0m0,005s

52 milissegundos contra 5 (o time mede quanto o comando levou; o real é o tempo de relógio). Para um programa que roda e termina, como um comando de terminal, faz diferença. As restrições do AOT são as do PublishTrimmed e mais algumas: a reflexão é limitada, e nada de carregar código novo em tempo de execução.

Missão: o programa abaixo sempre diz Modo: ?. Troque a linha por um bloco #if DEBUG … #else … #endif que mostre Modo: Debug numa configuração e Modo: Release na outra, como o modo.cs. Aqui, a saída deve ser Modo: Debug; publicado, o mesmo código diria Modo: Release.

Quando dá errado

error NETSDK1083: O RuntimeIdentifier 'linux-64' especificado não é reconhecido. 
$ dotnet publish -r linux-64
  Determinando os projetos a serem restaurados...
/usr/lib/dotnet/sdk/10.0.112/Sdks/Microsoft.NET.Sdk/targets/Microsoft.NET.Sdk.FrameworkReferenceResolution.targets(190,5): error NETSDK1083: O RuntimeIdentifier 'linux-64' especificado não é reconhecido. Consulte https://aka.ms/netsdk1083 para obter mais informações. [/home/ana/projetos/Escola/src/Escola.Relatorio/Escola.Relatorio.csproj]
«… a mesma linha, mais 3 vezes …»

O que aconteceu: o RID foi digitado errado: faltou o x de x64. A mensagem se repete porque cada etapa da restauração tropeça no mesmo erro.

Como resolver: use um RID da tabela da seção 2: -r linux-x64.

You must install or update .NET to run this application.

O que aconteceu: o programa foi publicado dependente do .NET (o dotnet publish simples) e levado para uma máquina sem o runtime do .NET 10. O lançador procurou o runtime, não achou, e mostrou a mensagem que você já viu na aula O Arquivo .csproj (lá, o programa pedia o .NET 8): "você precisa instalar ou atualizar o .NET", com o runtime que faltou (Microsoft.NETCore.App, versão…) e os que ele encontrou.

Como resolver: instale o runtime na outra máquina (sudo apt install dotnet-runtime-10.0) ou publique autocontido (-r linux-x64 --self-contained).

bash: ./Escola.Relatorio: Permissão negada

O que aconteceu: o arquivo perdeu a permissão de execução no caminho. Acontece ao copiar por um pendrive formatado para Windows, ou ao baixar de um site ou e-mail, que não guardam essa permissão (veja Instalar no Linux).

Como resolver: chmod +x Escola.Relatorio. Para não perder a permissão, mande a pasta dentro de um .tar.gz, como a Ana fez na seção 1: o tar guarda as permissões.

O executável aparado (ou AOT) falha, e o normal funciona

O que aconteceu: o PublishTrimmed ou o PublishAot cortaram algo que o programa usa por reflexão. Durante a publicação, o SDK costuma avisar com warning IL2026, IL3050 ou parecidos.

Como resolver: leia os avisos IL… da publicação. Muitas bibliotecas oferecem um jeito sem reflexão (o System.Text.Json, por exemplo, tem os "geradores de código", veja JSON). Se não houver, publique sem aparar.

Resumo

  • dotnet publish compila em Release e junta numa pasta tudo o que o programa precisa para rodar em outra máquina.
  • O padrão é dependente do .NET: pequeno (136 KB), mas a outra máquina precisa do runtime do .NET 10.
  • Autocontido (-r linux-x64 --self-contained) leva o runtime: 80 MB, roda em qualquer Linux x64.
  • PublishSingleFile junta num executável; PublishTrimmed corta o que não é usado; PublishAot gera código nativo (1,3 MB e começa em milissegundos).
  • O RID escolhe o sistema: linux-x64, linux-arm64, win-x64, osx-arm64. Dá para publicar para Windows a partir do Linux (menos com AOT).
  • Teste sempre o executável publicado, do jeito que ele vai ser entregue.

C# Parallel e PLINQ

Na aula Threads, você criou threads uma a uma. Mas o caso mais comum é bem mais simples: você tem uma lista grande e quer fazer a mesma conta em cada item, usando todos os núcleos do processador. Para isso, o .NET tem o Parallel (laços paralelos) e o PLINQ (LINQ paralelo), que dividem o trabalho entre as threads sozinhos. Nesta aula você vai contar os números primos até 3 milhões em um terço do tempo, reduzir fotos ao mesmo tempo e ver por que uma List comum não aguenta várias threads.

Você vai aprender
  • Trocar um for por Parallel.For e um foreach por Parallel.ForEach.
  • Rodar ações diferentes ao mesmo tempo com Parallel.Invoke, e limitar quantas rodam juntas com MaxDegreeOfParallelism.
  • Deixar uma consulta LINQ paralela com AsParallel, e manter a ordem com AsOrdered.
  • Medir o ganho, e quando o paralelo fica mais lento.
  • Guardar resultados sem condição de corrida: posições de um array, Interlocked, ConcurrentBag e o ToList do PLINQ.
  • O que acontece com as exceções: a AggregateException.

Esta aula usa for, foreach, lambdas, LINQ e a condição de corrida da aula Threads. Os programas rodam com dotnet run no notebook da Ana, com 8 núcleos. Os tempos e a ordem de algumas linhas mudam a cada execução.

No editor do guia, uma thread só

O .NET do editor roda em WebAssembly, com uma thread só. O Parallel e o PLINQ funcionam lá e dão os mesmos resultados, mas as voltas rodam uma depois da outra, na ordem, e o tempo não cai. Com uma thread só, também não há corrida: os erros da seção "Quando dá errado" ficam escondidos lá, e a exceção de uma volta do Parallel.For chega sem a AggregateException. Para ver a velocidade, a ordem misturada e esses erros, rode os exemplos no seu computador. As missões conferem os resultados, que são iguais nos dois lugares.

A ideia: a correção das provas

A professora tem 300 provas para corrigir. Sozinha, leva a tarde inteira. Ela chama mais 7 professores, divide a pilha em montinhos e cada um corrige o seu. A tarde vira meia hora. Ninguém precisa conversar com ninguém: cada prova é independente, e no fim basta juntar as notas.

O Parallel.For é essa divisão: ele reparte as voltas do laço entre as threads do pool (aula Task), uma por núcleo, mais ou menos, e só termina quando todas acabarem. Funciona bem quando as voltas são independentes, como as provas. Se cada volta depende da anterior (um saldo que vai sendo atualizado, por exemplo), o laço não pode ser dividido assim.

Parallel.For(0, 8, i => { … })
O mesmo que for (int i = 0; i < 8; i++) { … }, mas com as voltas espalhadas entre threads. O primeiro número é o começo (incluído), o segundo é o fim (não incluído), e a lambda é o corpo do laço, que recebe o i. A classe Parallel fica em System.Threading.Tasks, já incluído.
a ordem das voltas
As 8 voltas rodaram em 8 threads, e a ordem da saída mudou de uma execução para a outra. Não há "volta 0 primeiro": todas acontecem ao mesmo tempo. A própria thread principal (a 1) também ajuda.
Todas as voltas terminaram
O Parallel.For só devolve o controle quando todas as voltas acabaram. Não precisa de Join nem de await.

Guardar os resultados: cada volta na sua posição

Para guardar o que cada volta calculou, o jeito mais simples e seguro é um array do tamanho do laço: a volta i escreve só na posição i. Como nenhuma volta mexe na posição de outra, não há corrida, e o array termina na ordem certa, mesmo que as voltas tenham rodado misturadas.

Missão: o programa calcula os quadrados de 1 a 100 com um for comum. Troque o for por Parallel.For(0, quadrados.Length, i => { … });, com a mesma linha dentro. O resultado deve continuar Soma dos quadrados: 338350.

2. Quanto fica mais rápido?

Contar os números primos até 3 milhões dá bastante trabalho: para cada número, o programa tenta dividi-lo por vários outros. É o caso ideal: muitas contas independentes. O mesmo trabalho de três jeitos:

using System.Diagnostics;

const int Limite = 3_000_000;
Stopwatch relogio = Stopwatch.StartNew();
int sequencial = 0;
for (int n = 2; n <= Limite; n++)
{
    if (EhPrimo(n)) sequencial++;
}
Console.WriteLine($"for:          {sequencial} primos em {relogio.Elapsed.TotalSeconds:F2} s");

relogio.Restart();
int paralelo = 0;
Parallel.For(2, Limite + 1, n =>
{
    if (EhPrimo(n)) Interlocked.Increment(ref paralelo);
});
Console.WriteLine($"Parallel.For: {paralelo} primos em {relogio.Elapsed.TotalSeconds:F2} s");

relogio.Restart();
int plinq = Enumerable.Range(2, Limite - 1).AsParallel().Count(EhPrimo);
Console.WriteLine($"PLINQ:        {plinq} primos em {relogio.Elapsed.TotalSeconds:F2} s");

bool EhPrimo(int n)
{
    if (n < 2) return false;
    for (int d = 2; d * d <= n; d++)
    {
        if (n % d == 0) return false;
    }
    return true;
}

$ dotnet run primos.cs
for:          216816 primos em 1,10 s
Parallel.For: 216816 primos em 0,33 s
PLINQ:        216816 primos em 0,32 s
$ dotnet run primos.cs
for:          216816 primos em 1,08 s
Parallel.For: 216816 primos em 0,23 s
PLINQ:        216816 primos em 0,35 s
EhPrimo(n)
"É primo?": tenta dividir n por 2, 3, 4… até a raiz quadrada de n (d * d <= n). Se alguma divisão for exata, não é primo.
Interlocked.Increment(ref paralelo)
Várias voltas somam no mesmo contador ao mesmo tempo. Com paralelo++, haveria a condição de corrida da aula Threads e o total sairia errado. O Interlocked soma de forma atômica.
Enumerable.Range(2, Limite - 1).AsParallel().Count(EhPrimo)
A mesma conta em PLINQ (seção 4): os números de 2 a 3 milhões, contados em paralelo. O PLINQ cuida de juntar as contagens das threads, sem Interlocked.
1,1 s → 0,3 s
Três a quatro vezes mais rápido em 8 núcleos, e o mesmo resultado: 216816 primos. Não chega a 8 vezes porque dividir e juntar o trabalho custa um pouco, e os núcleos dividem outras coisas (memória, outros programas).

Quando o paralelo fica mais lento

Dividir o trabalho tem um custo fixo: acordar threads, repartir a lista, juntar os resultados. Se cada conta é muito rápida e há poucas, o custo de dividir é maior que o ganho:

using System.Diagnostics;

int[] numeros = Enumerable.Range(1, 1000).ToArray();
Stopwatch r = Stopwatch.StartNew();
long a = numeros.Sum(n => (long)n * n);
double t1 = r.Elapsed.TotalMilliseconds;
r.Restart();
long b = numeros.AsParallel().Sum(n => (long)n * n);
double t2 = r.Elapsed.TotalMilliseconds;
Console.WriteLine($"LINQ:  {a} em {t1:F3} ms");
Console.WriteLine($"PLINQ: {b} em {t2:F3} ms");

$ dotnet run pequeno.cs
LINQ:  333833500 em 1,360 ms
PLINQ: 333833500 em 17,901 ms

Somar mil quadrados é instantâneo, e o PLINQ foi 13 vezes mais lento. A regra: paralelize quando houver muito trabalho (muitos itens, ou cada item demorado), e meça antes e depois com o Stopwatch.

3. Parallel.ForEach e Parallel.Invoke

O Parallel.ForEach é o foreach paralelo, para qualquer lista. A Ana precisa reduzir 16 fotos para mandar por mensagem; cada uma leva 0,25 s (aqui simulado com Thread.Sleep):

using System.Diagnostics;

string[] fotos = Enumerable.Range(1, 16).Select(i => $"foto{i:00}.jpg").ToArray();
Stopwatch relogio = Stopwatch.StartNew();
foreach (string foto in fotos)
{
    Reduzir(foto);
}
Console.WriteLine($"foreach: {relogio.Elapsed.TotalSeconds:F1} s");

relogio.Restart();
Parallel.ForEach(fotos, foto => Reduzir(foto));
Console.WriteLine($"Parallel.ForEach: {relogio.Elapsed.TotalSeconds:F1} s");

relogio.Restart();
ParallelOptions opcoes = new ParallelOptions { MaxDegreeOfParallelism = 2 };
Parallel.ForEach(fotos, opcoes, foto => Reduzir(foto));
Console.WriteLine($"Parallel.ForEach com 2 de cada vez: {relogio.Elapsed.TotalSeconds:F1} s");

void Reduzir(string foto)
{
    Thread.Sleep(250);
}

$ dotnet run fotos.cs
foreach: 4,0 s
Parallel.ForEach: 0,5 s
Parallel.ForEach com 2 de cada vez: 2,0 s
Parallel.ForEach(fotos, foto => Reduzir(foto))
Cada foto da lista vai para uma volta, e as voltas se espalham entre as threads. 16 fotos em 8 núcleos: duas "rodadas" de 0,25 s.
new ParallelOptions { MaxDegreeOfParallelism = 2 }
"Grau máximo de paralelismo": no máximo 2 voltas ao mesmo tempo. Serve para não sobrecarregar algo que não aguenta muitos pedidos juntos (o disco, um servidor). 16 fotos, 2 de cada vez: 8 rodadas, 2 s.

Para fazer coisas diferentes ao mesmo tempo, e não a mesma coisa em vários itens, existe o Parallel.Invoke ("invocar"):

Parallel.Invoke(
    () => Console.WriteLine("Lavar a louça"),
    () => Console.WriteLine("Varrer a casa"),
    () => Console.WriteLine("Regar as plantas"));
Console.WriteLine("Faxina terminada");

$ dotnet run invoke.cs
Lavar a louça
Varrer a casa
Regar as plantas
Faxina terminada

Cada lambda é uma ação. Desta vez, a ordem saiu igual à do código, mas ela não é garantida. A única garantia é que Faxina terminada vem por último: o Invoke espera todas.

4. PLINQ: AsParallel

Se a conta já está escrita em LINQ, deixá-la paralela é uma palavra: AsParallel() ("como paralelo"). Tudo o que vem depois dele roda em várias threads:

int[] numeros = Enumerable.Range(1, 12).ToArray();
Console.WriteLine(string.Join(" ", numeros.AsParallel().Select(n => n * n)));
Console.WriteLine(string.Join(" ", numeros.AsParallel().AsOrdered().Select(n => n * n)));
Console.WriteLine(numeros.AsParallel().Sum(n => n * n));

$ dotnet run plinq.cs
1 4 9 25 49 81 100 121 144 16 36 64
1 4 9 16 25 36 49 64 81 100 121 144
650
$ dotnet run plinq.cs
1 9 25 49 81 100 121 144 4 16 36 64
1 4 9 16 25 36 49 64 81 100 121 144
650
numeros.AsParallel().Select(n => n * n)
Os quadrados, calculados em paralelo. A ordem do resultado embaralhou, e mudou entre as execuções: cada thread entregou o seu pedaço quando terminou.
.AsOrdered()
"Ordenado": as contas continuam em paralelo, mas o PLINQ devolve os resultados na ordem original. Custa um pouco de velocidade, por isso não é o padrão.
.Sum(…), .Count(…), .Max(…)
As agregações (aula Agregar) juntam os resultados das threads com segurança. Como somar não depende da ordem, o total é sempre o mesmo: 650.

O PLINQ também tem .WithDegreeOfParallelism(2), o equivalente do MaxDegreeOfParallelism, e .ToList() e .ToArray(), que juntam os resultados numa coleção com segurança (seção "Quando dá errado").

O que aconteceu: três execuções, três resultados: faltaram 15 mil itens, o programa quebrou, faltaram 84 mil. A List<T> (aula List) não foi feita para várias threads ao mesmo tempo. Quando ela enche, o Add cria um array maior e copia tudo para lá; se duas threads fazem isso juntas, uma atrapalha a outra. A AggregateException ("ocorreram um ou mais erros") junta as exceções de várias voltas.

Como resolver: três caminhos, do melhor para o pior:

  1. Deixe o PLINQ montar a lista: List<int> lista = numeros.AsParallel().Where(…).ToList();.
  2. Use um array do tamanho certo e grave cada volta na sua posição (resultado[i] = …), como na missão da seção 1.
  3. Use uma coleção feita para threads, do namespace System.Collections.Concurrent: ConcurrentBag<int> ("saco concorrente", sem ordem), ConcurrentQueue<T> ou ConcurrentDictionary<TKey, TValue>.
using System.Collections.Concurrent;

ConcurrentBag<int> saco = [];
Parallel.For(0, 100_000, i => saco.Add(i));
Console.WriteLine($"ConcurrentBag: {saco.Count}");

List<int> lista = Enumerable.Range(0, 100_000).AsParallel().Where(i => i % 2 == 0).ToList();
Console.WriteLine($"PLINQ ToList: {lista.Count}");

AggregateException: uma volta lançou uma exceção 
try
{
    Parallel.For(0, 10, i =>
    {
        if (i == 7) throw new InvalidOperationException($"Falhou na volta {i}");
    });
}
catch (AggregateException e)
{
    Console.WriteLine($"{e.InnerExceptions.Count} erro(s):");
    foreach (Exception erro in e.InnerExceptions)
    {
        Console.WriteLine($" - {erro.Message}");
    }
}

$ dotnet run exc.cs
1 erro(s):
 - Falhou na volta 7

O que aconteceu: quando uma volta lança uma exceção, o Parallel para de começar voltas novas, espera as que estão rodando e lança uma AggregateException com todas as exceções que aconteceram (várias voltas podem falhar ao mesmo tempo). Um catch (InvalidOperationException) não pegaria nada: o tipo que chega é AggregateException.

Como resolver: pegue AggregateException e olhe as InnerExceptions, ou trate o erro dentro da lambda, com um try em volta do trabalho de cada item.

No editor do guia é diferente: lá, o Parallel.For e o Parallel.ForEach deixam passar a exceção da volta sem o embrulho. O catch (AggregateException) do exc.cs não a pega, e o programa termina com Unhandled exception. System.InvalidOperationException: Falhou na volta 7 e o código 134. (O Parallel.Invoke e o PLINQ embrulham igual ao terminal.) Rode este exemplo no terminal.

Resumo

  • Parallel.For e Parallel.ForEach dividem as voltas de um laço entre os núcleos e só terminam quando todas acabam. As voltas precisam ser independentes, e a ordem entre elas não é garantida.
  • Parallel.Invoke roda ações diferentes ao mesmo tempo; MaxDegreeOfParallelism limita quantas rodam juntas.
  • AsParallel() deixa uma consulta LINQ paralela; AsOrdered() mantém a ordem. Count, Sum e ToList juntam os resultados com segurança.
  • Com muito trabalho, o ganho é grande (1,1 s → 0,3 s em 8 núcleos); com pouco, o paralelo fica mais lento. Meça.
  • Nada de List.Add ou total++ compartilhados: use posições de um array, Interlocked, coleções Concurrent… ou as agregações do PLINQ.
  • Exceções das voltas chegam juntas numa AggregateException. Para esperas (rede, disco), o caminho é async/await, e não o Parallel.

C# Testes (xUnit)

Toda vez que a Ana muda o boletim da escola, ela roda o programa, lança umas notas e confere a média de cabeça. Funciona, mas cansa, e um dia ela vai esquecer de conferir um caso. Um teste automatizado é um pedaço de código que faz essa conferência por ela: chama a função, compara o resultado com o esperado e diz "passou" ou "falhou". Com centenas deles, um único comando, dotnet test, confere o programa inteiro em segundos. Nesta aula você vai escrever testes com o xUnit, a biblioteca de testes mais usada no .NET.

Você vai aprender
  • Por que testar e o que é um teste de unidade.
  • A criar um projeto de testes com dotnet new xunit e ligá-lo à biblioteca que ele testa.
  • A escrever um teste com [Fact] e Assert.Equal, e a rodar com dotnet test.
  • A ler um teste que falha (Expected × Actual) e a consertar o código.
  • Um teste com vários valores ([Theory] e [InlineData]) e o teste de exceções (Assert.Throws).
  • --filter, --list-tests, os avisos xUnit2000 e xUnit1001 e a ideia do TDD.

Todas as saídas desta aula são reais, feitas com o .NET 10 SDK (10.0.112) e o xUnit 2.9.3 na máquina fictícia da Ana, na solução ~/projetos/Escola da aula Bibliotecas de Classes. O dotnet new xunit baixa pacotes do NuGet: na primeira vez, precisa de internet e pode demorar.

Por que testar?

Na aula de bibliotecas, a média do Beto, (5,0 + 7,5) ÷ 2 = 6,25, saiu 6,2. A escola arredonda para 6,3. Ninguém percebeu na hora, porque ninguém conferiu esse caso. Um teste é a anotação permanente "com as notas 5,0 e 7,5, a média tem de ser 6,3", conferida pelo computador toda vez.

Um teste de unidade (em inglês, unit test) testa um pedaço pequeno do código, como um método, sem tela, sem teclado, sem internet. É por isso que as regras ficam numa biblioteca: o projeto de testes a usa como qualquer outro programa.

Todo teste tem três partes, os três A:

  1. Arrange (preparar): criar o que o teste precisa (um boletim, algumas notas).
  2. Act (agir): chamar o que está sendo testado (ler a Media).
  3. Assert (afirmar): comparar o resultado com o esperado.

2. O primeiro teste de verdade: [Fact] e Assert.Equal

A Ana apagou o UnitTest1.cs e escreveu os testes do boletim. O terceiro é o caso do Beto:

namespace Escola.Notas.Tests;

public class BoletimTests
{

    public void Media_de_tres_notas_tem_uma_casa_decimal()
    {
        var boletim = new Boletim("Ana");
        boletim.Lancar(8.5m);
        boletim.Lancar(6.0m);

        Assert.Equal(7.9m, boletim.Media);

    [Fact]
    public void Sem_notas_a_media_e_zero()
    {
        var boletim = new Boletim("Ana");

        Assert.Equal(0m, boletim.Media);
    }

    [Fact]
    public void Media_6_25_arredonda_para_6_3()
    {
        var boletim = new Boletim("Beto");
        boletim.Lancar(5.0m);
        boletim.Lancar(7.5m);

        Assert.Equal(6.3m, boletim.Media);
    }
}
public class BoletimTests
Uma classe de testes: costuma ter o nome da classe testada mais Tests. Ela precisa ser public.
[Fact]
"Fato": um atributo (veja Atributos) que marca o método como um teste. Sem ele, o xUnit ignora o método.
public void Media_de_tres_notas_tem_uma_casa_decimal()
O nome do teste é uma frase que diz o que deve acontecer. Quando ele falhar, só o nome já explica o problema. Os _ são só para ler melhor.
var boletim = …; boletim.Lancar(…);
Arrange: preparar.
Assert.Equal(7.9m, boletim.Media);
Act e Assert: "afirme que são iguais". O primeiro argumento é o esperado; o segundo, o que o código deu. Se forem diferentes, o teste falha ali.

3. Vários valores num teste: [Theory] e [InlineData]

Para testar a Situacao, a Ana quer conferir vários casos: 7,0 (bem no limite) aprova, 6,9 não. Em vez de um [Fact] para cada, um [Theory] ("teoria") recebe os valores como parâmetros:

public class SituacaoTests
{
    [Theory]
    [InlineData(7.0, "Aprovado")]
    [InlineData(9.5, "Aprovado")]
    [InlineData(6.9, "Recuperação")]
    [InlineData(0.0, "Recuperação")]
    public void Situacao_depende_da_media(double nota, string esperado)
    {
        var boletim = new Boletim("Ana");
        boletim.Lancar((decimal)nota);

        Assert.Equal(esperado, boletim.Situacao);
    }

    [Theory]
    [InlineData(-1)]
    [InlineData(11)]
    public void Nota_fora_de_0_a_10_lanca_excecao(int nota)
    {
        var boletim = new Boletim("Ana");

        var erro = Assert.Throws<ArgumentOutOfRangeException>(() => boletim.Lancar(nota));
        Assert.Equal("nota", erro.ParamName);
    }
}
[Theory]
Um teste com parâmetros: ele roda uma vez para cada [InlineData].
[InlineData(7.0, "Aprovado")]
"Dados na linha": os valores de uma rodada, na ordem dos parâmetros (nota = 7.0, esperado = "Aprovado").
double nota … (decimal)nota
Um atributo não aceita valores decimal (o C# não deixa: 7.0m não pode ser argumento de atributo). Por isso o parâmetro é double, convertido para decimal dentro do teste (veja Conversão de Tipos).
Assert.Throws<ArgumentOutOfRangeException>(() => …)
"Afirme que lança": roda a lambda e passa se ela lançar essa exceção; falha se não lançar nada (ou se lançar outra). Ele devolve a exceção, para você conferir mais coisas nela.
Assert.Equal("nota", erro.ParamName)
Confere que a exceção fala do parâmetro certo.

5. As verificações mais usadas

VerificaçãoPassa quando…
Assert.Equal(esperado, obtido)Os dois são iguais.
Assert.NotEqual(a, b)São diferentes.
Assert.True(condição) / Assert.False(condição)A condição é true / false.
Assert.Null(x) / Assert.NotNull(x)x é / não é null.
Assert.Contains("Ana", texto)O texto (ou a lista) contém o item.
Assert.Empty(lista) / Assert.Single(lista)A lista está vazia / tem um item só.
Assert.Throws<TipoDaExceção>(() => …)O código lança exatamente essa exceção.
await Assert.ThrowsAsync<…>(() => …)O mesmo, para métodos async (o teste vira public async Task).
Assert.InRange(valor, mínimo, máximo)O valor está no intervalo.

6. A ideia do TDD

A Ana escreveu o teste do 6,25 antes de consertar o arredondamento: primeiro ele falhou, depois ela mudou o código, depois ele passou. Fazer isso de propósito, sempre, tem nome: TDD (Test-Driven Development, "desenvolvimento guiado por testes"). O ciclo tem três passos:

  1. Vermelho: escreva um teste para o que ainda não funciona. Rode: ele falha.
  2. Verde: escreva o mínimo de código para ele passar. Rode: todos passam.
  3. Refatorar: melhore o código (nomes, repetições) com os testes passando. Se algum falhar, você quebrou algo.

Ver o teste falhar primeiro é importante: um teste que nunca falhou pode estar testando a coisa errada (ou nada).

O que aconteceu: um método com [Fact] tinha um parâmetro (int nota). Um [Fact] não recebe valores: de onde viria a nota?

Como resolver: como a própria mensagem diz, tire o parâmetro ou troque para [Theory] com [InlineData(…)].

O teste não aparece no total

O que aconteceu: não há mensagem de erro: o teste novo simplesmente não roda. As causas comuns: faltou o [Fact] (ou [Theory]) em cima do método; o método ou a classe não é public; o projeto de testes não está na solução e você rodou dotnet test na pasta da solução.

Como resolver: dotnet test --list-tests mostra o que o xUnit encontrou. Se o teste não estiver na lista, confira o atributo e o public; se o projeto todo sumiu, dotnet sln list.

Referência rápida

Comando ou códigoO que faz
dotnet new xunit -o tests/Nome.TestsCria o projeto de testes.
dotnet reference add src/Nome --project tests/Nome.TestsLiga os testes ao que eles testam.

Resumo

  • Um teste automatizado confere um caso do seu código sempre que você roda dotnet test: preparar, agir, afirmar.
  • Projeto de testes: dotnet new xunit -o tests/Nome.Tests, dotnet sln add e dotnet reference add para a biblioteca testada.
  • [Fact] marca um teste; Assert.Equal(esperado, obtido) compara, com o esperado primeiro.
  • No teste que falha, leia o nome, o Expected, o Actual e a linha. Conserte o código (ou o teste, se ele estiver errado).
  • [Theory] + [InlineData] roda o mesmo teste com vários valores; Assert.Throws testa exceções.
  • --filter escolhe os testes; --list-tests mostra o que foi encontrado; os analisadores xUnit… avisam dos erros comuns.
  • TDD: vermelho (teste falha), verde (código passa), refatorar.
